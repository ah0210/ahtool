## 三、Win11 双击无反应：已定位根因

**根因（确定，代码级）**：Wails v2 的 `assetserver.NewAssetHandler` 在启动时要求
`go:embed` 的资产 FS 里存在 `index.html`；缺失时 `wails.Run` 返回
`no \`index.html\` could be found in your Assets fs.FS`。程序用 `-H windowsgui`
编译，没有控制台，`log.Fatal(err)` 的输出看不到，于是表现为“双击无反应”。

**为什么上一版会缺**：原项目把 `frontend/dist/index.html` 放在 `.gitignore` 里，
由已失效的 `build_frontend.js` 生成；上一轮清理时没有把它作为占位文件保留。
`main.go` 的中间件虽然会返回 `design/ui-prototype.html`，但 Wails 在中间件之前
先校验资产目录，缺 `index.html` 仍会启动失败。

**修复**：
- 新增 `frontend/dist/index.html` 占位文件（不会被用户看到，实际页面仍由中间件返回）；
- `frontend/dist/README.md` 写明“不要删”；
- 新增 `TestEmbeddedAssetsHaveIndexHTML` 回归测试；
- `main.go` 增加启动日志、panic 捕获、`wails.Run` 错误 MessageBox、`-diag` 环境报告。

**验证限制**：本环境无法在 Windows 上双击验证；但这条错误路径来自 Wails 源码，
不是猜测。新 exe 仍建议按下面步骤确认。

## 五、仍未完成 / 可行性判断

### A. 需要 Windows 真机（本环境不可行）

1. **运行 exe / GUI**：无 Windows、无 Wine；WebView2、UAC、窗口标题、页面渲染、诊断报告实际生成都未验证。
2. **工具真实执行**：SFC/DISM/bootrec/pnputil/服务/注册表写入结果未验证。
3. **Defender 实际拦截**：未做多引擎扫描；02 的归因是推断。
4. **驱动删除占用检查**：`pnputil /enum-devices /drivers` 的输出格式/语言差异未在真机核对；若枚举失败当前仍会继续删除（保守做法可改为“枚举失败也拒绝”）。
5. **`SpaceDelete` 的 FRN/路径一致性**：测试只覆盖纯索引解析；真机上长路径、8.3 名、大小写、 junctions 仍需验证。

**可行路径**：在 Windows 11 VM 中执行 `07` 的验证步骤；先 `-cli -nofull`，再逐项测试高风险工具；用 `go test -tags manual` 跑真机测试。

### B. 需要设计/数据模型改动（可行但工作量大）

6. **优化项全量原值快照**：当前 `Restore` 仍是固定常量。要真正“还原到用户原值”，需要：
   - 在 `execOptAction` 执行 `regwrite/regdelete` 前读取原值；
   - 存到 `%LOCALAPPDATA%\ahtool\opt_backup/<ts>.json`；
   - `RestoreOptimize` 优先应用快照，缺失时再回退固定 `Restore`；
   - 增加“备份/还原”单测（HKCU 测试键）。
   - 估算：1–2 天；风险：154 项动作类型多（regwrite/regdelete/service/cmd/shellnotify），要逐类型处理。
7. **`SpaceDelete` TOCTOU**：路径检查与删除之间仍可能被替换。彻底解决要用文件句柄/FRN 直接删除（`SetFileInformationByHandle`），工作量 2–3 天，且要处理跨卷/权限。
8. **同厂商关键词匹配收紧**：`appclean.go` 的残留/强制清理按 publisher/name 关键词命中，可能过宽；需要真机样本回归，工作量 2–3 天。
9. **Deep 预设中的安全项**：`safe-6..10`、`xingneng-30` 仍在 Deep 预设里。报告 `01/04` 建议移出默认勾选，但原项目把“151 项源名单 + Basic 87 / Deep 127”视为数据红线，本轮**未擅自改动**。若产品决策允许，把这几项 `Deep:false` 并同步测试/文案即可（半小时）。

### C. 需要外部条件

10. **代码签名**：需要 OV/EV 证书；无证书无法消除 SmartScreen/Defender 的“未知发布者”。
11. **多引擎基线 / 误报申诉**：需要 VirusTotal 账号、厂商申诉渠道。
12. **CI 实际运行**：workflow 已写，但本环境无法跑 GitHub Actions；Go 1.26.x 在 CI 上是否已可用需确认。

## 六、可行性结论

- **作为二次开发基线：可行。** 代码可编译、可测试编译、静态检查干净、文档与归档齐全。
- **作为“可直接发布给用户”的版本：尚不可行。** 缺 Windows 真机回归、代码签名、多引擎误报基线；优化项还原仍不是用户原值。
- **作为“安全审计交付”：基本可行。** 主要风险有代码/行号证据，修复边界清楚；未验证部分已明确标注，没有把推断写成事实。
